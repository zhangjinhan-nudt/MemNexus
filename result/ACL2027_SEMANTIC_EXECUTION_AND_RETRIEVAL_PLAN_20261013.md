# MemNexus：统一语义执行与前提驱动检索实施方案

日期：2026-10-13。本文基于当前源码、冻结的100题开发复测和当天检索到的原始论文材料。本文是实施设计，未修改生产算法，未运行新的付费实验，不将预期收益写成已取得的结果。

## 1. 决策与研究边界

建议建设轻量的统一语义执行内核，作为现有检索与回答流程的重构。复用QueryPlan、事实/来源存储、集合执行器、时间工具和AnswerTable；将它们的契约与执行结果统一，不增加独立服务、图数据库、多智能体编排或另一套记忆副本。

两项优化共享一个状态：查询需要哪些前提、哪些前提已经有支持、哪些仍未知、哪些候选被反驳。该状态同时驱动本地执行、检索补全和最终输出。

必要性来自实际机制缺陷，而不是模块缺失：

- 列表能回答三个狗名，计数仍输出2；两种操作没有共享成员集合。
- “十年前”的原文已在，规划出的两个槽位全被标为context，最终错误拒答。
- source quote存在，但不能证明所问主体参与了该事件。
- 时间计算拿到了数字，却可能使用错误事件或把发言时间当事件时间。
- fixed neighbour补充没有保证包含后续解释；词面missing_info也不能证明缺少语义前提。
- runtime构造了普通answer prompt和图/gate信息，但synthesize另行构造提示，没有使用前者；当前negative gate主要提供线索，所有返回路径blocked=false，不能将其称为可靠拦截器。

新内核只保证形式和操作的一致性；从自然语言识别主体、事件和关系仍可能错误，需要实证评估。引用可验证不等于自然语言蕴含已证明。

## 2. 科研依据与必须调整的新颖性定位

以下论文原始摘要/方法在本次检索中核对。最新两篇是2026年10月预印本，未独立复现其成绩；QGMem注明投稿TPAMI，不表示已录用。论文里的实验数字不能直接与本项目的DeepSeek结果比较。

| 工作 | 已核实的相关思路 | 在本项目中借鉴什么 | 适用边界 |
|---|---|---|---|
| [BFR, 2026-10-07](https://arxiv.org/abs/2610.09348v1) | 将问题拆为信息需求；FCA-MS组织互补候选；从未访问记录中进行文本、实体、session补充；按预算停止。主方法有固定访问日程，另测试状态条件化变体 | 区分候选池内组合与池外获取，显式去重和累计证据 | 与“缺失前提补检索”高度重合；不能再以这句话本身作为新颖性。BFR明确不假设能识别真实充分性 |
| [QGMem, 2026-10-08](https://arxiv.org/abs/2610.11920v1) | 事件原子记忆、事实/发言双时间、动态状态轨迹；混合召回、rerank与工作记忆局部图 | 保留可连接事件字段、时间语义和来源；图只构建在相关工作集合上 | 事件图和查询相关图已经存在，不据此声称创新；不照搬其图编码器/训练成本 |
| [SimpleMem, 2026, v3](https://arxiv.org/abs/2601.02553v3) | 语义结构压缩、多视图索引、query-aware检索；v3实现设置为窗口20、Qwen3-Embedding-0.6B/1024维、检索3–20 | 压缩索引与原始来源互补，保留低成本候选生成 | 主要baseline。锁定论文版本、代码commit及实际配置；本项目替换DeepSeek模型且之前仅取D1–D5的开发协议，不能称严格复现原论文成绩 |
| [HippoRAG 2, 2025](https://arxiv.org/abs/2502.14802) | PPR关联检索、更深的passage integration和在线LLM使用 | 连接结构化关系和原文片段，防止多跳增强损害直接事实问答 | 共享实体/图邻接只产生候选，不能直接认定实体同一或事实成立 |
| [LightMem, ICLR 2026](https://arxiv.org/abs/2510.18866) | 轻量分组、主题短期记忆、离线长期整合 | 将稳定可复用绑定尽可能移出重复在线调用 | 首阶段不改写入算法，先隔离回答端收益；离线成本仍须统计 |
| [Reproducing LightMem, 2026-07-31](https://arxiv.org/abs/2607.29104v1) | 在其复现实验中检索器影响很大，原始turn检索可与构造记忆竞争；压缩可能丢失答案信息 | 原文RAG必须加入控制；测试相同检索器和相同token预算 | 这是其设置中的实证发现，不能推广成所有记忆系统都无用 |
| [Sufficient Context, 2024/2025](https://arxiv.org/abs/2411.06037) | 区分上下文不足与模型未利用充分上下文；研究充分性与拒答 | 同时标注缺证据、误用证据、错误拒答，避免只看retrieval hit | 不要求每轮额外付费做充分性裁判；运行时依靠操作前提，评估时才做独立标注 |
| [A-MEM, NeurIPS 2025](https://arxiv.org/abs/2502.12110) | 结构化笔记、动态链接、记忆演化 | 关系可逐步组织，并保存链接来源 | 动态链接不是新颖性，不能把相似关系当等价关系 |

建议研究假设：**将可执行的答案义务、主体/事件绑定、集合和时间操作与检索缺口统一，能否在相同预算下减少语义错误和答案不一致？**

可能的区别在于：BFR解决取得充分集合的问题，我们进一步研究取得证据后，能否由同一绑定状态执行不同答案操作，并将操作无法执行的原因反馈给检索。QGMem用局部图增强生成，我们研究带类型前提的执行和检查。以上是待验证的差异，不是已经完成的新颖性证明。相关工作全文和代码对照、等预算消融仍必需。

## 3. 最小表示：一个查询契约、一份绑定状态

### 3.1 QueryContract：融入现有QueryPlan

建议字段：

- `requested_outputs`：用户直接要求的输出。每项必须有稳定ID、结果类型、必需标志、对应问题原文位置；不得由生成器任意改成context。
- `constraints`：主体身份/角色、关系、事件条件、时间、状态、集合范围；每项保留来源于问题的依据。
- `requirements`：得到输出所需的前提。包含对象类型、变量、证据要求；不包含预期答案或预期成员数。
- `operations`：一个有界、无环的小型操作序列，引用requirements或前一步结果；不生成或执行Python/SQL代码。
- `answer_policy`：查事实、允许标注推断、显式选择题，以及部分答案/未知的表达规则。

首版仅支持select/filter、join、project、union/distinct、count、time_of/time_difference/start_year。条件复杂且代数无法表达时，用带来源的自由文本项，并明确标记为模型解释结果，不伪装成确定性证明。

真实Planner完成第一次语义解析；本地检查变量、类型、循环、必需输出和明显问句类型冲突。保持一般问题可表达，避免把所有“which/how many”强制转成某个索引查询。

### 3.2 BindingState：改造现有AnswerTable

每个前提记录：

```
requirement_id
bindings: entity_id / event_id / value
support: fact_id:version + turn_id + event_index + quote_span
support_status: supported | unknown | contradicted | ambiguous
decision_origin: stored_verified_structure | model_interpretation
missing_reason: actor | relation | event | time_anchor | member_scope | evidence
```

“支持”表示在当前解释与证据下被接受；只有类型、索引来源、授权、精确引文和数值计算等部分是机械可验证的。模型对自然语言的解释仍需保留不确定性。

证据/问题匹配可以是一组来源共同成立：某条引入实体、下一条使用代词，两条合在一起支持绑定。仅逐条检查会错失组合证据。

事件角色采用actor/recipient/object等少量常用字段；alias和事件同一性有来源证明或模型解释记录，不能仅用名字相似、同一段落或共享实体直接合并。

### 3.3 完整性的三个不同层面

1. `output_coverage`：所有用户必需输出都有答案或明确缺口。
2. `execution_ready`：每个操作的输入与限定满足、没有未解决的歧义/冲突。
3. `enumeration_scope`：集合是明确总量、给定范围内的闭合枚举，还是已知子集。

读取完一个索引分区、没有找到新证据、达到检索预算均不证明自然语言答案穷尽。集合闭合需要明确的量词/范围声明，或任务给定封闭范围且相关记录已经解析；有未解析关系或身份时保留unknown/lower_bound。

### 3.4 计数和时间的执行规则

- count必须消费集合结果的ID；不能由模型直接填写一个与成员清单无关的数字。显式总数声明也须绑定主体、对象范围和时间，照片可见数默认是观察子集。
- 同一snapshot、scope、as_of、relation下的列表与计数复用同一集合标识；不同问法的parser若编译不同，记录跨问题不一致，不能伪称本地执行就保证自然语言等价。
- 日期端点绑定event_id和time_role，区分发生时间、发言时间和有效时间；出现在来源中的日期不自动是所求事件日期。
- 精确日期差才直接计算；区间差返回区间，模糊“上周”保留解释和精度；按年倒推只能支持相应年份精度。
- ambiguous/unknown不视为false；不因检索未命中而宣布事实不存在。explicit contradiction只否定对应候选，不自动否定整段历史。

## 4. 前提驱动检索的具体流程

```
query -> 一次planner产生QueryContract
      -> 既有hybrid召回、授权过滤和原文回填
      -> 一次binder产生BindingState（复用当前synthesize调用）
      -> 本地执行与检查
         -> ready: 本地渲染
         -> gap且有预算: 本地缺口检索 -> 一次增量binder -> 本地执行
         -> 预算耗尽/无进展/仍歧义: 输出已支持部分及缺口状态
```

简单事实若已有可信、版本有效且满足完整契约的结构，可走本地快速路径。不能仅因单一predicate有唯一命中就跳过语义检查。

### 4.1 缺口类型与检索动作

| 缺口 | 动作 | 新记录需要补什么 |
|---|---|---|
| 主体/指代不明 | 实体及局部上下文查找 | actor与mention的绑定前提 |
| 事件只知泛称 | 事件索引及问答/解释邻接 | 该事件的object、result或具体内容 |
| 时间端点缺失 | 同一事件的时间视图 | 明确日期/相对时间＋合法锚点 |
| 成员不全 | 关系族与归属实体检索、增删状态轨迹 | 新成员、同一性、范围边界 |
| 状态冲突 | 版本、有效时间和原文更正 | 哪个状态在所问时点成立 |
| 有证据但绑定失败 | 候选关系/别名或局部组合重新绑定 | 解释误差；不无条件扩大检索 |

新查询由缺口、已绑定变量和原问题限定生成，保留说话人、对象和时间条件；不从暂定答案倒推确认性查询，不使用gold。

### 4.2 有界证据选择

候选来自既有稀疏/稠密/符号索引，外加未访问的原文视图。semantic similarity负责候选排序，不能作为支持事实的阈值。

给候选证据组g一个可调启发式优先级：

```
priority(g) = [新增可执行输出的权重 + 部分缺口覆盖 - 冗余惩罚]
              / 预计新增输入、输出与调用成本
```

不同类型缺口采用可观测规则或经开发集校准的支持估计；未经校准的LLM confidence不当成概率。原文选入前就需要做的语义判断，尽量与现有binder调用合并；本地候选排序只预测潜在覆盖。

关键：两条记录可能只有合用才产生收益。首版按显式依赖生成少量证据对/组，并对最小缺口做一层前瞻，避免逐条贪心把互补证据都视为无收益。限定候选池不超过现有120、每轮补充最多3个查询、证据组深度最多2作为首轮开发配置；这些值需敏感性分析，不宣称最优或普适。

不要套用普通集合覆盖的近似保证：支持关系可能依赖模型判断，互补前提使效用未必满足次模性。可在固定绑定和明确依赖的受限版本分析性质，主系统收益以消融验证。

### 4.3 停止条件

- 用户必需输出的操作前提满足、无相关冲突：停止补检索；状态仅相对于契约与当前证据，不称全局事实完备。
- 第一轮补充没有新增授权来源、绑定或可执行输出：停止并记录no_progress。
- 达到预设调用/token/费用上限：停止并记录budget_exhausted，不把它改写成“对话未提及”。
- 首版检索最多两轮、模型通常planner＋binder两次；仅有真实gap时最多增加一次增量binder。保留一次schema修复时必须同计入预算。

对于枚举，未发现新成员不能单独作为完整性证据。报告已知成员与范围状态；准确率评测仍按预注册的统一答案协议，不为了通过gold临时放松规则。

## 5. 避免冗杂：替换哪些逻辑

| 文件 | 改造方向 | 合并/退役的重复逻辑 |
|---|---|---|
| models.py | 在QueryPlan中加入契约，复用Evidence/FactMember | required_info、query_constraints、collection qualifier的语义逐步归并 |
| synthesis.py | 统一绑定状态、执行检查与最终渲染 | 字符串含数字/单位就通过的弱检查；answer/context任意切换 |
| composition.py | 抽出可复用集合算子 | 逐来源裁决与新答案表的双重生成路径 |
| temporal.py | 承担全部时间运算及精度传递 | synthesis中的临时正则年份推导逐步迁移 |
| grounding.py | 原文验证、缺口动作与预算选择 | _missing词覆盖降为特征；固定邻接仅作候选生成 |
| reasoning.py | 实体/事件候选关系与本地绑定辅助 | 正则路由仅作回退；negative gate名称和语义与实际功能一致 |
| runtime.py | 一个直接问答执行入口 | 为synthesis构造后未使用的普通prompt、平行完整性判断和无效图计数 |
| providers.py | planner编译契约、binder填事实、增量binder补缺口 | 对整个证据重复做compose与synthesize |
| store.py | 按需增加可重建实体/事件投影，复用SQLite事务 | 不建第二套事实真值库 |

迁移时允许临时保留legacy适配器以便回归；验证通过后收敛到一个线上入口。消融通过显式组件开关控制，不维护多个长期独立系统。

复用约束：tenant/owner/project/session、memory version、有效期、retracted/pending等过滤必须在每次补检索和增量绑定前执行。缓存键包含scope、query contract、snapshot与证据版本；版本变化必须失效。原始支持永久可追溯，撤回证据不能沿旧绑定继续支持答案。

## 6. 可复用结果与实际效率

第一阶段不改变写入流程，固定记忆库隔离问答收益。第二阶段再把稳定且有来源的实体/事件绑定变成可重建投影，随memory版本增量更新。只有这一步才有机会减少多题重复解释成本；不能把本地执行自动等同于整体token下降。

增加上下文带来的收益已经在开发集出现，但当前总token仍高于SimpleMem。新方案重点是：

- 用可复用fact/event ID与quote span替代重复长引文。
- 本地去重、集合操作和时间计算，不为这些确定性步骤调用模型。
- gap-free问题保持两次或更少模型调用，缺口问题才用第三次。
- 成功的绑定按scope/snapshot缓存，质量主实验关闭答案缓存，效率实验单独披露冷/热状态。
- 预算对实际发给provider的序列化消息计量，包含schema、修复和潜在输出；不再只统计未被synthesize使用的旧header。

SimpleMem比较成本为预先在开发集测得的同协议工作负载基准，不能逐测试题借助baseline答案或耗时自适应分配资源。正式比较建库、问答、更新和失败重试分别记账；不同问答次数报告摊销曲线。API估算价与实际账单分开。

## 7. 分阶段实现与验收

### 阶段A：契约和统一执行入口（建议3–5个工作日）

实现requested_outputs与requirements分离，接通统一检查；移除“所有slot都是context但正常返回未提及”的路径；修正实际prompt计量。先保留现有候选集合，不同时扩大召回。

验收：每个必需输出要么执行出值，要么有明确gap；伪造引用、跨主体确定性不匹配、未授权来源不通过；action_plan兼容；旧scope/version测试不退步。

### 阶段B：集合/实体/事件与时间算子（建议5–7个工作日）

让列表与count共享集合ID；为事件时间端点建立角色；支持未知身份、部分成员和区间。优先复用已有FactSemantics及Evidence，不先迁移所有历史数据。

验收：在固定绑定层，成员排序/重复引用不影响答案；增加/移除一名已辨实体影响count；主体换成另一人不能沿用旧绑定；source date不自动成为event date。自然语言变形测试单独报告parser和binding错误，不能只测执行器。

### 阶段C：缺口驱动补检索（建议5–7个工作日）

从操作失败原因产生Gap记录，复用索引做一次有界补充和增量绑定；预算/无进展终止。

验收：只读取新增候选；没有缺口的题不增加调用；具有互补前提的受控样本能找到组合；预算耗尽与无事实声明分开；记录每次补充解决的缺口和新增token。

### 阶段D：成本优化、消融与冻结（建议3–5个工作日）

做ID化序列化与版本缓存、清理重复路径；通过后冻结源码和配置，进入真实对比。以上时间是实施估计，不是质量提升承诺。

## 8. 实验矩阵与ACL论证

### 8.1 基线

1. SimpleMem：锁定论文版本和代码commit；既报告适配同DeepSeek/Qwen的公平比较，也区分原论文复现设置。
2. Raw-turn RAG：同embedding与生成模型，原始话轮可检索，不压缩；检验复杂记忆组织是否必要。
3. 当前78/100版本：冻结为开发消融基线，不能再把其100题当独立测试。
4. BFR：最接近前提补全思想的对照，应优先复现公开代码；若暂不可运行，只能标注为忠实机制适配，不能声称作者原始实现。
5. QGMem/HippoRAG2：选与最终方法最接近且可复现的一项验证结构优势，避免第一阶段同时接入过多系统。

### 8.3 数据与指标

- 旧100题作开发回归，全部重测并报告修复与退步；修复题不能替换旧错题拼接成绩。
- LoCoMo所有已研究的对话标记为开发暴露；从同对话抽新题不是对话级held-out。
- 使用官方LongMemEval-S与尚未分析的对话/数据集，按session/user来源划分开发与测试后封存；不事后用test选阈值。
- LoCoMo/LongMemEval按官方评测规则报告；主语义裁判与词面指标分开。旧固定A/B对抗协议作为单独历史协议，不冒充官方统一主分数。
- 附加成员precision/recall、主体/事件绑定错误、列表—计数一致性、错误拒答、错误肯定、时间精度/区间错误和补检索收益。
- evidence hit/turn recall不等价于答案语义已在；抽样人工标记答案句及必要组合，评测标注不能进入模型运行。
- 成本统计含写入、检索时模型、schema修复、失败重试与本地索引开销。报告实际输入/输出token、调用、P50/P95、每正确答案成本，以及预算曲线。
- 根据对话/用户聚类计算配对区间；只有10个LoCoMo对话簇时说明不稳定性，增加题目并不等于增加独立样本量。第二个backbone验证方法迁移。

### 8.4 可证伪的假设与继续条件

H1：固定证据下，统一执行降低主体/事件/计数错误，且不通过大量拒答换取precision。

H2：等token/等费用下，前提驱动检索比原检索及最近邻补全方法更有效地增加可执行输出和最终正确答案。

H3：上述收益在独立对话和另一个数据集/模型上保持，整体费用不超过预注册的SimpleMem参考预算。

H4：在固定语义绑定和snapshot下，列表/计数/时间操作满足明确的不变量；自然语言到绑定的误差率独立报告。

若B与A无差异，而D只在给更多token时提高，不能主张语义执行贡献；若原文RAG已达到相同质量/成本，需解释存储/更新/复用上的其他价值，或简化方法；若只有旧100题提高，应停止继续针对旧题调参。
